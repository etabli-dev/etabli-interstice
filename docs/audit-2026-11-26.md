# Test-runtime audit — 2026-11-26

Scope: task planning and persistence, calendar ingestion, authentication and request boundaries, MCP, model proposals, container settings and trial deployment. This review does not qualify the service for production replacement.

## Findings corrected

| Finding | Impact | Correction |
| --- | --- | --- |
| Non-ASCII login tokens raised a comparison error | Unauthenticated requests could cause HTTP 500 | Compare encoded bytes; malformed credentials remain unauthorized |
| Login, patch and proposal routes assumed JSON objects | Arrays and scalars could cause HTTP 500 | Validate request shapes before handling |
| Repeated credential values were accepted for different roles | Role depended on configuration ordering | Reject duplicate credentials at startup |
| Dependency traversal used recursion | Valid chains near the 1,000-task limit failed | Iterative traversal, including cycle and shared-predecessor coverage |
| Some CalDAV item failures lacked property status | A failed response could replace busy time with an empty snapshot | Reject incomplete items and missing calendar data; retain prior snapshot |
| Valid zero-duration events rejected the entire feed | A single instantaneous event prevented calendar updates | Preserve event without reserving busy time |
| Progress totals were queried separately for every task | Repeated scans grew with task and receipt counts | Indexed receipts and one aggregated task query |
| Provider timeout indistinguishable from invalid output | Troubleshooting could not distinguish latency and format failures | HTTP 504 for timeout; HTTP 502 for other provider failures |
| Configured model displayed as connected | Interface overstated verified availability | Explicitly label availability as unverified |

Calendar requests now have a 30-second overall network deadline in addition to per-I/O timeouts. Read-only users no longer see the calendar refresh action.

## Evidence

The expanded suite contains 28 tests. Against the prior runtime, the new cases produced three failures and three errors; all 28 pass after correction. Model tests use simulated timeout, invalid-output and successful-output responses and verify that none writes tasks. Calendar tests exercise partial responses, duration, recurrence, daylight saving and instantaneous events. Existing MCP scope, cookie-origin, progress replay, revision and backup checks remain passing.

A local single-process scenario with 1,000 independent 30-minute tasks took approximately 1.88 seconds and returned 640 blocks plus 360 explicit shortages. This is a narrow local observation, not a VPS latency guarantee or worst-case performance bound.

Calendar semantics were checked against [RFC 5545 section 3.6.1](https://www.rfc-editor.org/rfc/rfc5545#section-3.6.1). Provider request and response fields were checked against the [Ollama chat API](https://docs.ollama.com/api/chat). No proprietary implementation was used.

## Remaining acceptance gates

- Live inference remains unqualified. Earlier requests timed out; the shared VPS was under substantial load during this audit. Load is a contributing hypothesis, not a proven root cause. The separate inference service and its resource limits were not changed.
- Focus integration, recurring tasks, real iCloud/Nextcloud qualification, persisted stable plans and migration remain unfinished.
- Browser actions use server idempotency, but a fresh click after an ambiguous network failure can generate a new operation. Inspect task/progress state before repeating it; durable browser retry recovery remains required before production.
- Calendar parsing and plan computation do not yet have isolated CPU/memory deadlines. Response size and recurrence limits reduce exposure but do not prove worst-case bounds. Administrator-configured sources remain a trust boundary.
- Calendar snapshots retain previous data on error and expose freshness; stale snapshots do not make a plan authoritative.
- Authentication is scoped bearer credentials and short-lived browser sessions. OAuth enrollment and device credential lifecycle remain pending.
- This audit is not a full penetration test, dependency vulnerability attestation, legal clearance or production capacity qualification.

External calendar writes remain absent. Production consumers must stay on their current provider until the migration gates are met.
